# ۰۹ — قواعد کار عامل‌های AI

مستندات tool-agnostic است. هر عامل کدنویس باید همین قواعد را رعایت کند.

## نقش‌ها

| نقش | اجازه |
|-----|-------|
| مالک | مدیریت پروژه، brief، قرار دادن design، unlock تصمیم جدید، تأیید انتشار/اقدام برگشت‌ناپذیر، قفل مشخصات پیش‌نویس‌شده |
| AI | نوشتن کد و تست طبق docs-v2 + design؛ **بوت‌استرپ اسکلت مونوریپو** وقتی مالک شروع می‌گوید (`12`)؛ کشف موجودی UI on-demand؛ پیش‌نویس مشخصات گم‌شده برای قفل مالک؛ گزارش کمبودها؛ **به‌روزرسانی STATUS و handoff** هنگام تعویض AI یا پایان جلسه (`13`) |

AI مالک پروژه نیست؛ معماری قفل‌شده را باز نکند. **مالک مدیریت می‌کند؛ AI بعد از قفل کد می‌نویسد.**

## ترتیب کار

1. **خواندن تدریجی** طبق [`11-context-and-reading.md`](./11-context-and-reading.md): پاس اول README → `00-locks` → `01-product` → **`STATUS.md`** (تداوم؛ [`13-handoff.md`](./13-handoff.md)). کل docs-v2 را یک‌جا نخوان. به حافظهٔ chat بین ابزارها تکیه نکن.
2. قفل را اجرا کن؛ برای قفل‌شده سؤال نپرس.
3. **شروع از صفر / bootstrap:** اگر مالک trigger بوت‌استرپ گفت («شروع پروژه»، bootstrap، اسکلت، …): کارstream اول [`12-bootstrap.md`](./12-bootstrap.md) است — طرح اسکلت بده، تأیید بگیر، **AI** (نه مالک) scaffold خالی بسازد؛ بدون feature code و بدون Docker. بعد کارstreamهای بعدی per `11`.
4. اگر مالک کارstream دیگر گفت (API / mid / android-low / …): اول **طرح + task breakdown** بده، تأیید بگیر، **بعد** deep-read فایل‌های جدول نوع‌کار.
5. اگر موضوع **unlock‌نشده** یا مبهمِ خارج قفل است: کار قفل‌شده را انجام بده، فرض خطرناک نساز، و سؤال را کوتاه در گزارش بیاور.
6. **مشخصات گم‌شده** (endpoint dump، schema DB، env، …): پیش‌نویس سند در docs-v2 (یا مسیر توافق) → قفل مالک → سپس پیاده‌سازی. در کد به‌صورت خاموش اختراع نکن.
7. **شروع کلاینت/UI:** ابتدا موجودی کامل طبق [`10-ui-discovery-rules.md`](./10-ui-discovery-rules.md) — docs کاتالوگ پر ندارد.
8. UI فقط با `design/` پس از موجودی و دارایی متناظر.
9. ماژولار بنویس؛ سرویس‌ها و اپ‌ها را قاطی نکن.
10. **Handoff / پایان جلسه:** قبل از بستن session یا وقتی مالک بگوید، `STATUS.md` را طبق [`13-handoff.md`](./13-handoff.md) به‌روز کن (done / in progress / next / قفل‌های تازه / سؤالات باز / مسیرهای کلیدی). AI جدید از STATUS ادامه می‌دهد، نه از chat.

## انضباط توکن و حافظهٔ کاری

| باید | نباید |
|------|--------|
| سقف تقریبی فایل per turn از `11` را رعایت کن | dump-read همهٔ `06-domains` یا کل بسته |
| خلاصهٔ کوتاه working memory نگه دار (قفل‌های اثرگذار، فایل‌های خوانده، فرض‌ها، پیش‌نویس‌های باز) | هر نوبت قفل‌های تغییرنیافته را کامل بازخوانی کنی |
| بعد از تأیید کارstream فقط فایل‌های لازم را deep-read کن | بدون طرح/تأیید مالک به عمق بروی |
| کمبود کاتالوگ را به‌صورت سند پیش‌نویس گزارش و قفل بخواه | endpoint/schema/env را فقط داخل کد حدس بزنی |
| STATUS را بخوان و قبل از پایان جلسه به‌روز کن (`13`) | به حافظهٔ chat بین AIها / ابزارها تکیه کنی |

جزئیات جداول نوع‌کار و سقف فایل: `11-context-and-reading.md`. تداوم چند-AI: `13-handoff.md`.

## پیش‌نویس مشخصات گم‌شده (با مالک)

نبودن dump endpoint / schema کامل / فهرست env در docs **عمدی** است (`00-locks`, `07`). وقتی کارstream به آن‌ها نیاز دارد:

1. پیش‌نویس را به‌صورت فایل markdown در `docs-v2/` (یا مسیر توافق‌شده با مالک) بنویس.
2. از مالک قفل/اصلاح بخواه.
3. فقط پس از تأیید پیاده‌سازی کن.

همین الگو برای هر قرارداد جدیدی که در قفل‌ها نیست اعمال می‌شود.

## موجودی UI (قفل کشف)

| باید | نباید |
|------|--------|
| وقتی مالک شروع کلاینت می‌گوید، موجودی کامل اسکرین+کامپوننت آن scope را تولید کن | کاتالوگ پر ثابت در docs بنویسی یا از docs انتظار داشته باشی |
| همه اپ‌های scope (android + web) + shared + guest gates + حالت‌های ثانویه | فقط صفحات اصلی را لیست کنی و OTP/device/step-up/empty/offline را جا بیندازی |
| خودممیزی در برابر `03-features` و سؤالات باز قبل از نهایی | بدون audit موجودی را «تمام» اعلام کنی |
| کد UI فقط با ID موجودی + فایل design | اسکرین بدون design یا خارج موجودی |

جزئیات قالب جداول و چک‌لیست: `10-ui-discovery-rules.md`. تحویل design: `08-design-handoff.md`.

## ماژولار بودن

| باید | نباید |
|------|--------|
| مرز `api-low` / `api-mid` / `api-high` | import مستقیم کد سرویس دیگر |
| اپ Android جدا (`ir.isra.low|mid|high`) | یک ماژول UI مشترک اجباری بین سه اپ بدون تصمیم مالک |
| `web-main` ≠ `web-admin` | کپی ادمین داخل سایت اصلی |
| auth همه کلاینت‌ها فقط به low؛ بقیه به سطح خود | mid/high غیر-auth به low یا برعکس |
| packages فقط با توجیه | shared god-library |
| inter-service: internal REST + outbox/inbox | EventEmitter بین‌سرویسی؛ Redis/broker اجباری |
| pnpm + Turborepo؛ بدون Docker اجباری فعلی؛ بوت‌استرپ فقط scaffold | تحمیل Docker؛ feature code داخل bootstrap؛ واگذاری ساخت اسکلت به مالک وقتی trigger گفته |

پکیج‌های اختیاری مجاز: `packages/jwt-verify`, `packages/api-types`.

00-locks.md > بقیه docs-v2 > STATUS.md > design مالک > فرض AI / حافظهٔ chat > new docs/ قدیمی

## وقتی باید بپرسی

فقط وقتی:

- تصمیم در قفل‌ها نیست و روی امنیت/داده اثر دارد
- دو تفسیر معتبر از brief مالک وجود دارد
- دارایی design لازم است و موجود نیست (بپرس/گزارش کن، UI جعلی نساز)
- پس از خودممیزی موجودی UI، سؤال باز باقی مانده
- مشخصات گم‌شده را پیش‌نویس کرده‌ای و نیاز به قفل/اصلاح مالک داری
- کارstream را پیشنهاد داده‌ای و قبل از deep-read/کد به تأیید نیاز داری
- طرح بوت‌استرپ را داده‌ای و قبل از ساخت پوشه‌های ریشه به تأیید نیاز داری
- STATUS ناقص/متضاد با ریپو است و برای ادامه mid-stream نیاز به Clarification داری (`13`)

نپرس برای چیزهایی که جدول قفل جواب داده (مثلاً ۳ اپ Android، هفته شنبه، Nest×۳، Faraz OTP، RS256، Socket.IO روی mid، وزن ۴۰/۳۰/۳۰، نقش ارزیابی).

## کیفیت کد مورد انتظار

1. TypeScript سخت در Nest و SvelteKit؛ Kotlin idiomatic در Compose.
2. اعتبارسنجی ورودی در مرز API.
3. خطای استاندارد `07-api-conventions.md`.
4. تست حداقل برای auth، حضور یک‌باره‌امتیاز، مجوز صف/ارزیابی (supporter+teacher)، عدم ارزیابی manager alone.
5. لاگ بدون PII حساس (OTP کامل، توکن خام).
