# ۱۰ — قواعد کشف موجودی UI (برای AI پیاده‌ساز)

این سند **کاتالوگ پر از اسکرین نیست**. فهرست کامل UI را مالک یا docs از پیش پر نمی‌کنند. وقتی مالک درخواست شروع یک کلاینت (مثلاً `android-low` یا کل سطح low) را می‌دهد، **همان AI پیاده‌ساز** باید ابتدا موجودی کامل را طبق این قواعد تولید کند.

## قانون اجباری

```
درخواست شروع کلاینت / UI
  → ۱) تولید موجودی کامل اسکرین + کامپوننت برای همان scope
  → ۲) خودممیزی در برابر چک‌لیست ویژگی‌ها + سؤالات باز
  → ۳) مالک از روی موجودی در design/ طراحی می‌کند
  → ۴) AI فقط با دارایی design متناظر، UI کد می‌کند
```

- **قبل** از هر درخواست design و **قبل** از هر کدنویسی UI: موجودی کامل.
- بدون ردیف موجودی + دارایی `design/` متناظر: اسکرین/کامپوننت کد نشود.
- docs-v2 و این فایل جایگزین موجودی پر نیستند؛ روش‌شناسی کشف‌اند.

## دامنه scope

وقتی مالک می‌گوید مثلاً «شروع کلاینت low» یا «شروع android-mid»:

| الزام | توضیح |
|-------|-------|
| همهٔ اپ‌های آن scope | مثلاً برای سطح low: `android-low` **و** بخش low در `web-main` |
| برای mid | `android-mid` + بخش mid در `web-main` |
| برای high | `android-high` + `web-admin` |
| design-system مشترک | کامپوننت‌های shared در همان تحویل موجودی (حتی اگر بعداً در `design/components/` بیایند) |

اگر مالک صریحاً فقط یک اپ را نام برد، همان اپ + وابستگی‌های shared لازم برای آن اپ.

## روش استخراج (چک‌لیست — چیزی جا نماند)

AI باید **همه** منابع زیر را قدم‌به‌قدم راه برود و برای هر قابلیت، اسکرین‌ها و حالت‌ها را استخراج کند:

1. **`03-features.md`** — هر ردیف ویژگی → اسکرین(های) اصلی + ثانویه
2. **`06-domains/`** مربوط به سطح — مسئولیت API و داده → صفحات مصرف‌کننده
3. **`04-platforms.md`** — تفاوت Android / Web / PWA برای همان سطح
4. **`05-auth-security.md`** — OTP، رمز، refresh، لیست دستگاه/نشست، step-up، revoke
5. **قفل Guest (`00-locks` #20)** — محتوای قابل‌مرور مثل عضو؛ اقدام‌های gated → مسیر ثبت‌نام/ورود
6. **ماتریس نقش** — Guest / عضو / `session_manager` / `session_supporter` / `teacher` / `quran_student` / نقش سیستم — چه کسی چه می‌بیند
7. **حالت‌های سراسری** — loading، empty، error، offline، permission denied، نگهداری
8. **اسکرین‌های ثانویه (اجباری — حذف ممنوع)** از جمله:
   - OTP درخواست / تأیید / تلاش مجدد / قفل پس از ۳ تلاش
   - ورود با رمز / فراموشی رمز
   - لیست دستگاه‌ها و نشست‌ها / revoke
   - step-up
   - empty states (صف خالی، بدون جلسه، اینباکس خالی، بدون نشان، …)
   - offline / خطای شبکه
   - permission denied / بدون نقش جلسه
   - تأییدهای مخرب (خروج، revoke همه)
   - onboarding حداقلی پروفایل پس از اولین ورود
   - Guest CTA ثبت‌نام روی اقدام gated

## قالب خروجی الزامی

موجودی را به صورت جداول Markdown با ID پایدار انگلیسی تحویل بده.

### الف) اسکرین‌ها

| screen_id | سطح | اپ‌ها | عنوان فارسی | نقش‌های مجاز | حالت‌ها | کامپوننت‌های کلیدی | وابستگی design | یادداشت |
|-----------|-----|-------|-------------|--------------|---------|---------------------|----------------|---------|
| `low_home` | low | android-low, web-main | خانه | guest, member | default, loading, empty, error, offline | `comp_app_bar`, … | `design/low/low_home*.png` | … |

### ب) کامپوننت‌های design-system / shared

| component_id | حوزه | عنوان فارسی | variants / states | استفاده در screen_idها | وابستگی design |
|--------------|------|-------------|-------------------|------------------------|----------------|
| `comp_primary_button` | shared | دکمه اصلی | default, disabled, loading | … | `design/components/...` |

### ج) تفاوت Guest در برابر عضو

| screen_id یا اقدام | Guest می‌بیند؟ | Member | رفتار gated |
|--------------------|:--------------:|:------:|-------------|
| مرور لیست جلسات | ✓ | ✓ | — |
| ثبت حضور | ✗ (CTA ثبت‌نام) | ✓ | → signup/login |

### د) ماتریس نقش × اسکرین (برای mid/high اجباری‌تر)

| screen_id | guest | student | manager | supporter | teacher | system_admin |
|-----------|:-----:|:-------:|:-------:|:---------:|:-------:|:------------:|
| … | | | | | | |

### ه) خودممیزی تکمیل بودن (قبل از نهایی‌کردن)

| منبع چک‌لیست | پوشش داده شد؟ | شکاف / سؤال باز |
|--------------|:-------------:|-----------------|
| هر بخش `03-features` | ✓/✗ | … |
| auth + OTP + devices + step-up | ✓/✗ | … |
| guest gates | ✓/✗ | … |
| empty/error/loading/offline/denied | ✓/✗ | … |
| صف / ارزیابی / امتیاز مطابق قفل نقش | ✓/✗ | … |
| همه اپ‌های scope | ✓/✗ | … |
| shared components | ✓/✗ | … |

**بدون جدول خودممیزی + فهرست سؤالات باز، موجودی نهایی محسوب نمی‌شود.**

## ارتباط با design و کد

1. AI موجودی را تولید و به مالک می‌دهد.
2. مالک از روی موجودی دارایی را در `design/` می‌گذارد (`08-design-handoff.md`).
3. AI اسکرینی را کد نمی‌کند مگر `screen_id` در موجودی باشد **و** دارایی design متناظر موجود باشد.
4. اگر design ناقص است: همان بخش را نساز / صریحاً «منتظر design» — UI جعلی نساز.
