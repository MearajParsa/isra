# ۱۱ — خواندن تدریجی و حافظهٔ کاری (Context)

هدف: AI پیاده‌ساز **هرگز** کل `docs-v2` را یک‌جا نخواند. خواندن باید token-efficient، progressive، و وابسته به کارstream باشد. مالک مدیریت می‌کند؛ AI بعد از قفل و تأیید، کد می‌نویسد.

## قانون اجباری

| باید | نباید |
|------|--------|
| فقط فایل‌های لازم برای همان نوبت/کارstream را بخوان | dump-read کل پوشه یا همهٔ `06-domains/` بدون نیاز |
| اول پاس اجباری کوچک، بعد جدول نوع‌کار | از README مستقیم به عمق API/UI بپری |
| طرح + breakdown بده، تأیید مالک بگیر، بعد deep-read | بدون تأیید مالک فایل‌های زیاد را باز کنی |
| خلاصهٔ کوتاه working memory نگه دار؛ قفل‌های تغییرنیافته را دوباره نخوان | هر نوبت `00-locks` را از صفر بازخوانی کامل کنی اگر قبلاً خلاصه کرده‌ای |
| کاتالوگ‌های گم‌شده را **پیش‌نویس سند** کن و قفل مالک بگیر | در سکوت داخل کد endpoint/schema/env اختراع کنی |
| `STATUS.md` را در پاس اول بخوان؛ قبل از پایان جلسه به‌روز کن (`13`) | به chat memory بین ابزارها تکیه کنی یا STATUS را نادیده بگیری |

## پاس اول اجباری (همیشه — کوچک)

در **هر** شروع کار یا session جدید (از جمله AI تازه‌وارد پس از تعویض ابزار)، این‌ها را بخوان (به همین ترتیب):

1. [`README.md`](./README.md) — نقشه و ارجاع به این سند
2. [`00-locks.md`](./00-locks.md) — منبع حقیقت
3. [`01-product.md`](./01-product.md) — محصول، سطوح، غیرهدف‌ها
4. **`STATUS.md`** — وضعیت زنده (معمولاً `docs-v2/STATUS.md` یا ریشهٔ ریپو؛ ببین [`13-handoff.md`](./13-handoff.md))

بعد از پاس اول: **متوقف شو** مگر مالک کارstream مشخص کرده باشد یا STATUS کار باز داشته باشد که مالک ادامهٔ همان را خواسته. اگر فقط سؤال کلی است، از همین فایل‌ها جواب بده. **هرگز** به حافظهٔ chat AI قبلی تکیه نکن.

اگر مالک تازه «شروع پروژه» گفته و مونوریپو اسکلت ندارد: کارstream اول **bootstrap** است — [`12-bootstrap.md`](./12-bootstrap.md) را پس از طرح+تأیید deep-read کن (نه قبل از تأیید، مگر برای نوشتن طرح کوتاه).

سپس [`09-ai-working-rules.md`](./09-ai-working-rules.md) را در صورت نیاز به قواعد اجرا بخوان (نه به‌جای پاس اول). برای تعویض AI / ادامه mid-stream / اصلاح کار قبلی: [`13-handoff.md`](./13-handoff.md).

## وقتی مالک کارstream می‌گوید

مثال‌ها: «شروع پروژه / bootstrap / اسکلت» (کارstream اول از صفر — `12`)، «بریم سراغ API»، «mid را شروع کنیم»، «android-low»، «auth»، «web-admin».

ترتیب تعامل:

1. **طرح پیشنهادی** کوتاه (هدف، مرز سرویس/اپ، ریسک‌ها، خروجی‌های قفل‌شدنی).
2. **Task breakdown** شماره‌دار (قابل تأیید تکی).
3. **سؤال تأیید** از مالک — بدون تأیید، deep-read و کد نکن.
4. بعد از تأیید: فقط فایل‌های جدول نوع‌کار زیر را deep-read کن.
5. اگر کاتالوگ لازم نیست (endpoint dump، schema DB، env): **پیش‌نویس سند** در `docs-v2` (یا مسیر توافق‌شده) → قفل مالک → سپس پیاده‌سازی.

نقش: مالک مدیریت و قفل می‌کند؛ AI کد می‌زند **بعد از** قفل.

## جدول خواندن بر اساس نوع کار

پس از پاس اول + تأیید کارstream:

| نوع کار | بخوان (به ترتیب پیشنهادی) | بعد چه کن |
|---------|---------------------------|-----------|
| **Bootstrap / شروع از صفر** | `12-bootstrap` (+ در حد طرح: چیدمان از `02`؛ design خالی از `08`) | طرح اسکلت → تأیید مالک → AI scaffold خالی (apps/services/packages?/design/media/docs-v2) → بدون feature/Docker → پیشنهاد کارstream بعدی |
| **API / بک‌اند کلی** | `02-architecture` → `05-auth-security` → `06-domains/` مرتبط → `07-api-conventions` | پیش‌نویس endpoint + schema (سند جدید) → تأیید مالک → کد |
| **دامنه low** | `06-domains/low.md` → بخش‌های مرتبط `03-features` → `05` / `07` در حد نیاز | همان؛ اختراع خاموش ممنوع |
| **دامنه mid** | `06-domains/mid.md` → `03-features` مرتبط → Socket/realtime از `02`/`00` | پیش‌نویس قرارداد mid → قفل → کد |
| **دامنه high** | `06-domains/high.md` → نقش/مجوز از `05` و `01` | پیش‌نویس admin API/schema → قفل → کد |
| **Auth / امنیت** | `05-auth-security` → قفل‌های auth در `00` → `07` (مسیرهای auth) | بدون تغییر قفل OTP/JWT |
| **Android (هر سطح)** | `04-platforms` → `09` → `10-ui-discovery-rules` (+ `08` و `THEME_TOKENS` وقتی به UI رسیدی) | ابتدا موجودی UI on-demand؛ بعد design مالک |
| **Web main / admin** | `04-platforms` → `09` → `10` → `08` → `THEME_TOKENS` | مثل Android؛ مرز `web-main` ≠ `web-admin` |
| **UI / design فقط** | `08-design-handoff` → `10` → `THEME_TOKENS` | بدون دارایی `design/` اسکرین کد نکن |
| **ویژگی محصول** | بخش مرتبط `03-features` → دامنهٔ `06` همان ویژگی | اگر API لازم است به ردیف API برو |
| **تم / توکن بصری** | `THEME_TOKENS.md` (+ `08` در صورت نیاز) | بدون unlock توکن قفل را عوض نکن |

فقط **فایل‌های دامنهٔ لازم** از `06-domains/` را باز کن (مثلاً API mid → `mid.md`؛ نه هر سه مگر کار چندسطحی تأیید شده باشد).

## سقف فایل در هر نوبت (راهنما)

| مرحله | حداکثر تقریبی | توضیح |
|-------|---------------|--------|
| پاس اول | ۴ فایل (+ STATUS) | README + 00 + 01 + STATUS |
| پیشنهاد طرح کارstream | ۰–۲ اضافه | در حد نیاز برای طرح؛ deep-read نه |
| پس از تأیید مالک | ۳–۵ فایل deep-read | بیشتر فقط با دلیل در گزارش |
| پیاده‌سازی ادامه‌دار | ۱–۳ فایل جدید/نوبت | اگر working memory کافی است بازخوانی نکن |

اگر برای یک تصمیم به بیش از ۵ فایل تازه نیاز دیدی: خلاصه کن، از مالک اولویت بپرس، و خواندن را چندنوبتی کن.

## Working memory (حافظهٔ کاری کوتاه)

پس از خواندن، یک یادداشت کوتاه داخلی نگه دار (و در گزارش به مالک خلاصه بده اگر مفید است):

- قفل‌های اثرگذار روی این کارstream (bullet)
- فایل‌های خوانده‌شده + تاریخ/نوبت
- فرض‌های تأییدشده vs باز
- پیش‌نویس‌های سند در انتظار قفل
- مسیرهای کد/ماژول هدف

**قفل‌های تغییرنیافته را دوباره کامل نخوان** — از همین یادداشت استفاده کن. فقط اگر مالک قفل را عوض کرد یا تعارض دیدی، `00-locks` را بازخوانی کن.

یادداشت داخلی **جایگزین STATUS پایدار نیست**. قبل از پایان جلسه یا handoff، همان نکات را در `STATUS.md` بنویس تا AI بعدی (احتمالاً ابزار دیگر) ادامه دهد — [`13-handoff.md`](./13-handoff.md).

## جدول نوع‌کار — ادامه / handoff

| نوع کار | بخوان | بعد چه کن |
|---------|--------|-----------|
| **تعویض AI / session جدید با کار باز** | پاس اول + STATUS → فقط فایل‌های نوع‌کار فعلی per جدول بالا | از آخرین Next/In progress ادامه؛ chat قبلی را منبع نگیر |
| **ادامه API mid-stream** | STATUS → پیش‌نویس اشاره‌شده → ردیف API | از task تأییدشده؛ دوباره اختراع نکن |
| **اصلاح کار قبلی** | STATUS + مسیرهای کلیدی → فایل‌های دامنهٔ مربوط | فیکس محدود مگر مالک بازنویسی بخواهد |
| **پایان جلسه / handoff صریح** | — | STATUS را کامل به‌روز کن (`13`)؛ deep-read جدید لازم نیست |

## کاتالوگ‌ها و مشخصات گم‌شده

نبودن این‌ها در docs-v2 **عمدی** است تا وقتی کارstream شروع شود با مالک ساخته شوند:

| کمبود رایج | رفتار AI |
|------------|----------|
| dump / فهرست endpoint | پیش‌نویس سند (مثلاً زیر `docs-v2/` یا مسیر توافق) → تأیید/قفل مالک → بعد implement |
| schema DB / موجودیت‌ها | همان |
| env / پیکربندی اجرا | همان |
| کاتالوگ اسکرین | طبق `10-ui-discovery-rules.md` (on-demand)، نه invent در کد |

**ممنوع:** پر کردن سکوت با حدس داخل کد، OpenAPI جعلی بدون قفل، یا «بعداً درست می‌کنیم» بدون سند.

جزئیات قفل منفی endpoint dump: `00-locks.md` و `07-api-conventions.md`.

## تعامل با مالک (خلاصه)

```
مالک: کارstream را نام می‌برد
  → AI: طرح + breakdown + سؤال تأیید
مالک: تأیید / اصلاح
  → AI: deep-read محدود + در صورت نیاز پیش‌نویس مشخصات
مالک: قفل مشخصات
  → AI: پیاده‌سازی ماژولار + گزارش
```

برای موارد ازپیش‌قفل در `00-locks` سؤال نپرس. برای مشخصات غایب و تصمیم unlock‌نشده: پیش‌نویس بده و بپرس — کد نزن.
